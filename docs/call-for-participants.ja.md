# HBMの予想を改善する情報を募集します

[English](call-for-participants.md) · [現在のランキング](current-ranking.ja.md) · [出典](sources.md) · [参加方針](../CONTRIBUTING.md)

**特定の製品・製造ロットに、公称容量を超える通常データ用HBMが実装されている可能性はあるか。** 本プロジェクトは、公開仕様と当時の部品性能を照合し、通常構成では説明しにくい観測から未検証の予想を立てます。v0.10で類似性による旧順位を撤回し、候補別の反対モデルと不足情報を公開しています。物理的に載っていること、正常に動くこと、実際に利用できることは別の主張です。

募集するのは、**予想の根拠を強める資料と、普通の構成で説明できる反例の両方**です。実機所有者の既存の観測も歓迎します。実機や成功報告がなくても参加できます。

## まず一つの情報から

[簡易報告のIssueを開く](https://github.com/Unjuno/hbm-anomaly-research/issues/new?template=quick-evidence.md)。最初は次の4点だけで構いません。

1. どの製品・仮説についての情報か。
2. 資料や観測から、実際に何が確認できたか。
3. 資料のURLと該当箇所、または識別情報を伏せた既存のログ・写真。
4. その情報で予想のどこが変わり、何が未確認のままか。

不明な項目は「不明」で構いません。日付のある公式資料、部品型番の対応表、通常の低密度構成、順位を逆転させる反論も有用です。予想に資料を引用していても、その資料の著者が同じ予想をしているとは限りません。

詳しい予想は[候補・反論・出典訂正](https://github.com/Unjuno/hbm-anomaly-research/issues/new?template=new-candidate.md)、既存の実機観測は[実機報告](https://github.com/Unjuno/hbm-anomaly-research/issues/new?template=hardware-observation.md)を使えます。詳細欄を初回からすべて埋める必要はありません。

## 今、どの情報があると判断が変わるか

根拠と反対材料は[現在のランキング](current-ranking.ja.md)にあります。以下は確認したい点であり、追加容量があると断定する表ではありません。

| 対象 | 最初に欲しい情報 | 区別したい説明 |
| --- | --- | --- |
| H100 SXM5 64 GB HBM2e | 実在する物理ボードの正確な型番と、既存資料・刻印によるHBM構成 | 64 GBの物理ボードか仮想割当か。通常構成か、より大きな実装か |
| CMP 100-200 | 約6 GB級の個体と対応付けられた部品型番・密度情報 | 通常の低密度部品か、より大きな実装の一部公開か。帯域だけでは密度は決まらない |
| A30、PG199 / DRIVE A100、A800 40GB Active、H100 SXM5 80 GB | 特定リビジョンの部品対応表、または既存のパッケージ情報 | 未実装・ダミーか、追加の実HBMか。同系統の製品というだけでは不足 |
| AMD MI50 16 GB | 特定個体のメモリ部品情報。分かれば修理・換装歴 | 普通の16 GB実装か、高密度実装か。既に32 GBとして動く個体の古いラベルは容量復元ではない |
| Intel GPU Max 1100 | 無効化された第4スタックの密度を直接特定する資料 | 公式に記載された無効スタックの容量・状態。恒久無効化の記載は解除可能性の根拠にはならない |
| H20 / MI308の供給監視 | 再利用された材料・転用先・製造段階を特定する公開資料 | 特定製品の部材置換か、再販・別材料の再利用・会計上の変化か |

## 実機所有者は、既に分かっている情報から

製品名、公称容量、基板型番、ドライバ表示容量と単位、未改造・改造済み・不明の区分、観測日が役立ちます。ドライバや実行環境、物理ボードか仮想環境かも、分かる範囲で添えてください。既存のメモリ部品刻印や写真があれば特に有用です。バス幅や部品の外形だけから密度を決めないでください。

新規購入、分解、ファームウェア変更、クロック変更、ドライバ入れ替えは必要ありません。NVIDIA・AMD・Intelとも、現在の環境のツールや手元の資料で確認できる情報だけで参加できます。[実機観測の補助資料](validation.md)は、詳しい報告を解釈するための資料です。全手順の完了を参加条件にはしません。

HBMの製造日、パッケージの日付、基板の組立日、ファームウェアのビルド日、購入日は区別します。日時には出典と精度を添え、読み方の根拠がない刻印からロットを推測しないでください。

## 否定的・未確定の情報も残します

| 観測 | 言えること | それだけでは言えないこと |
| --- | --- | --- |
| ドライバが公称どおりの容量を表示 | 現在の設定で公開されている容量 | 余分なHBMが物理的に存在しないこと |
| 関連する通常データ用メモリ部品をすべて同定し、合計が公称容量と一致 | 部品同定と範囲確認が正しければ、その個体の通常構成 | 他リビジョン・他ロットもすべて同じこと |
| 公称より大きい実メモリ構成を同定 | 部品同定が正しければ、その個体の物理余剰 | 余剰領域の正常性・利用可能性 |
| 初期化やメモリ確保に失敗 | その環境での失敗 | 追加部品の不存在や、すべての環境での恒久的失敗 |
| 既存の管理された読み書き実験で追加常駐容量を報告 | 記載された条件・範囲内の結果。[判定条件](validation.md)による解釈が必要 | 全領域の正常性、全ロットの成功率、メーカーがその構成にした理由 |

普通だった例、矛盾する例、情報不足の例も受け付けます。競合する説明を区別できなければ「未判定」とします。容量表示の変化だけを動作確認へ格上げしません。

## 公開に必要な情報だけを共有してください

シリアル番号、UUID、ホスト名、個人情報などの識別情報は削除してください。公開できる権利のある資料だけを使ってください。公開URL、権利上適切な範囲の短い引用、識別情報を伏せた観測、自分の考察で十分です。非公開のファームウェアやベンダーのバイナリは不要です。

考える問いは一つです。**この情報によって、予想のどの前提が変わるでしょうか。**
